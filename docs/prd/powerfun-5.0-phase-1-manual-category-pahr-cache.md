## 1．背景

当前系统自动分类主要依据标题、距离和整场平均心率，无法可靠识别含热身／恢复段的节奏课和间歇课：

- 2026-11-06，`659451010`：节奏课被分为有氧耐力跑；
- 2026-11-09，`660460268`：节奏课被分为有氧耐力跑；
- 2026-10-29，`656543045`：间歇课被分为轻松跑。

Pa:Hr 还存在两个独立问题：

1. 当前公式中负值代表后半程效率下降，但问题探测只检查 `> +5%`，导致负向漂移漏报；
2. 节奏课使用整场分圈，混入热身和恢复；间歇课的工作／恢复结构也不适合整场 Pa:Hr。

此外，LLM 缓存只校验活动、体感和 Prompt 版本。人工课型、工作段或分析算法改变后，旧点评仍可能被复用。正常最新深析与指定日期深析存在重复实现，若分别修补会再次分叉。

## 2．本批目标

1. 用小型、可追踪的人工配置覆盖节奏跑和间歇跑，不改其他自动分类逻辑。
2. 普通课型 Pa:Hr 保持原输入和数值；节奏跑只算人工工作段；间歇跑默认不适用。
3. 修复负向 Pa:Hr 漂移漏报。
4. 当前活动和历史 Pa:Hr 图共用同一选段规则。
5. 分析事实变化后缓存必须失效，事实不变时缓存继续命中。
6. 正常最新深析复用 `_generate_deep_report()`，避免两套实现。

## 3．明确不做

本批执行会话不得顺带实现以下事项：

- 不修改 `_calc_short_term()`、`_calc_long_term()`、`_calc_yoy()`、`_calc_percentile()` 的统计门槛或 verdict；
- 不实现跨温“能力证据不足”、逐月剔除敏感性、同比多月份门槛或百分位 n≥10；这些属于第二批；
- 不修改 `src/chart_generator.py` 的分圈统计、IQR、P20—P80 或平滑逻辑；
- 不修改 `RunClassifier` 的既定自动分类规则；
- 不自动识别节奏段、间歇组或恢复段；
- 不建立温度修正模型；
- 不修改负荷、技术变化、强度结构、FIT 补拉逻辑；
- 不批量重生成历史报告，不删除正式缓存，不回写历史 parquet；
- 不修改 `VERSION`，不提升 `LLM_PROMPT_VERSION`；
- 不引入外部模型 API、PDF、iCloud、定时任务或新重型依赖。

## 4．F1：人工课型覆盖配置

### 4.1 配置文件

新增可由 Git 跟踪的：

`config/activity_overrides.toml`

使用 Python 3.14 标准库 `tomllib` 读取，不新增 YAML 等依赖，也不使用会被当前 `.gitignore` 排除的 JSON。

初始内容：

```toml
schema_version = 1

[activities."659451010"]
category = "tempo_run"
pa_hr_laps = [4, 9]

[activities."660460268"]
category = "tempo_run"
pa_hr_laps = [5, 11]

[activities."656543045"]
category = "intensity_run"
```

`pa_hr_laps` 是包含起止 `lap_index` 的二元数组，两端均包含。它不是自动识别结果，而是人工确认的训练工作段。

### 4.2 配置语义

- 只允许覆盖为现有键 `tempo_run` 或 `intensity_run`；
- `tempo_run` 的人工显示名为“节奏跑”；
- `intensity_run` 的人工显示名为“间歇跑”；
- 人工覆盖优先级高于自动分类；
- 未配置活动完全维持原分类；
- 不全局修改 `RunClassifier.CATEGORIES`，避免把其他自动“强度训练”都改名为间歇跑。

### 4.3 应用位置与数据列

在统一报告入口 `_run_reports()` 内、任何深析／综合报告使用 DataFrame 之前，以复制方式应用覆盖，确保正常模式、`--load-parquet`、指定日期和批量模式使用同一有效课型。

每行保留：

```text
category_auto      原 parquet／自动分类
category_source    auto 或 manual
category           实际生效分类
category_name      实际生效显示名
```

为节奏跑／间歇跑附加人工 Pa:Hr 起止圈字段，供当前活动和历史图共同读取。字段可为 `pa_hr_lap_start`／`pa_hr_lap_end`，也可采用等价的明确结构化方式，但不得只在某一条报告路径临时传参。

要求：

- 应用函数幂等，重复调用不会把已覆盖分类误存为 `category_auto`；
- 不修改 parquet，不在报告生成后把人工分类保存回主表；
- 若 `stats` 中含课型相关统计，覆盖后需同步重算；纯总量统计不得重复计算或改写；
- 当前数据中不存在的配置 activity_id 只警告，不阻断其他活动；
- 配置无法解析、category 不允许、段落不是两个正整数或起点大于终点时，必须在报告前给出清晰错误并停止，不得静默忽略。

## 5．F2：Pa:Hr 双轨与统一选段

### 5.1 统一规则

实现一个供当前活动与历史趋势共同调用的选段函数，规则如下：

| 有效课型 | 输入分圈 |
|---|---|
| 轻松跑、LSD、比赛、有氧耐力跑及其他未覆盖课型 | 全部有效分圈，保持现状 |
| `tempo_run` | 仅人工 `pa_hr_laps` 指定的连续分圈 |
| `intensity_run` 且未指定连续段 | 不计算 |
| `intensity_run` 且明确指定连续稳态段 | 仅计算该人工段，不回退整场 |

现有 `_calc_pa_hr()` 的距离中点拆分、速度／心率加权及公式保持不变。本批改变的是输入段落，不是另造公式。

### 5.2 缺失与异常

- 节奏跑缺少人工段：不计算，原因 `missing_manual_segment`；
- 人工段没有匹配分圈、有效距离不足 3 km 或有效心率不足：不计算，保留具体原因；
- 间歇跑未指定连续段：不计算，原因 `interval_not_applicable`；
- 任何人工课型都不得在选段失败后静默回退整场；
- 不适用不能用 0 表示。

增加简洁的结构化上下文，例如：

```python
{
    'scope': 'full_activity' | 'manual_segment' | 'not_applicable',
    'segment_laps': [4, 9] | None,
    'reason': None | 'missing_manual_segment' | 'interval_not_applicable' | 'insufficient_lap_data',
}
```

字段名可等价调整，但必须可测试、可进入报告和 Prompt。

### 5.3 当前报告与历史图

- 当前活动 Pa:Hr 使用统一选段；
- `_build_pa_hr_history_chart()` 中每个历史活动也使用同一函数；
- 间歇跑无有效 Pa:Hr 时不进入历史趋势点；
- 节奏跑历史点使用人工工作段，而非整场；
- 计算成功的 Pa:Hr 字典需带段落说明，报告显示“整场”或“人工工作段第 X—Y 圈”；
- 节奏跑／间歇跑未计算时，报告和 Prompt 应显示简短原因，不得仅静默隐藏指标。

普通活动缺少分圈时，可保持现有降级展示，不扩大本批模板改造。

## 6．F3：修复负向漂移探测

`src/deep_analyzer.py` 的问题探测改为：

```python
pa_pct <= -ISSUE_PA_HR_PCT
```

同步修正：

- 常量注释；
- `_detect_issues()` docstring；
- 问题标题中的数值符号和阈值，示例应为 `-6.1%（阈值 -5%）`；
- evidence 不得再写正号或把“效率下降”描述成正向漂移；
- 不修改 Pa:Hr 的现有 verdict 分档和公式。

边界要求：

- `-5.00%` 触发；
- `-4.99%` 不触发；
- 正值不触发该负向漂移问题；
- `None`／不适用跳过。

点评只能将 Pa:Hr 作为本次效率漂移证据，不得仅凭该指标确诊热疲劳、过度训练或能力下降。

## 7．F4：缓存增加分析数据哈希

### 7.1 哈希对象

在调用 `_resolve_llm_report()` 前，基于当次结构化 `analysis_data` 计算稳定 SHA-256：

- 使用确定性的序列化方式，键排序一致；
- 兼容 numpy／pandas 标量和日期；
- 不包含瞬时 HTML、输出路径、当前时间或 response 内容；
- 在 `brief_summary` 等后加字段写入前计算；
- 人工课型、Pa:Hr 段落或参照结果变化，应通过 `analysis_data` 自然改变哈希。

不需要额外把整份 parquet 或所有原始活动纳入哈希，避免无关活动变化导致全部缓存失效。

### 7.2 缓存格式

现有三行 frontmatter 后新增：

```text
analysis_hash: <sha256>
```

读取缓存时必须同时满足：

- activity_id 对应同一缓存文件；
- `prompt_version` 匹配；
- `analysis_hash` 匹配；
- `user_note_hash` 继续遵循现有规则：本次显式传 note 时必须匹配，未传 note 时保持现有复用语义。

旧缓存没有 `analysis_hash`，按未命中处理，不报错、不删除旧文件。

`_write_llm_request()` 的 `context.json` 和 `--llm-response` 的上下文校验也必须加入 `analysis_hash`，防止把旧分析生成的 response 写到新分析上。

### 7.3 版本纪律

- 六小节和 `<<<BRIEF>>>...<<<END>>>` 协议不变；
- `LLM_PROMPT_VERSION` 保持 12；
- 现有“基线数据变化不升 Prompt 版本”的测试原则继续成立；
- 不得用全量 Prompt 版本升级替代分析哈希。

## 8．F5：合并正常最新深析入口

`_run_reports()` 中“正常模式：最近一次跑步”的重复实现改为复用 `_generate_deep_report()`。

要求：

- 指定日期、latest、批量和正常最新深析共用同一分析路径；
- 保持现有输出文件命名和 `deep_only` 行为；
- fetcher 的创建与关闭责任明确，不引入未关闭连接；
- 缓存命中时不重复准备模型请求；
- 缓存未命中时仍遵守现有 prepare／response 两阶段协议；
- 不改变综合报告后续步骤。

这是合并重复代码，不允许借机重写报告模板或调整第二批统计口径。
